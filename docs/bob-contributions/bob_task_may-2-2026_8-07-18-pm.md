I've identified the **root cause** of the location search failure:

### **Primary Issue: Nominatim User-Agent Policy Violation**

The backend is using **Nominatim** (OpenStreetMap's geocoding service) with a generic user-agent string:

```python
geolocator = Nominatim(user_agent="astrophotography-target-finder")
```

**Why this causes failures:**

1. **Nominatim Usage Policy**: Nominatim requires a unique, identifiable user-agent that includes contact information. Generic user-agents like "astrophotography-target-finder" are often **rate-limited or blocked** to prevent abuse.

2. **No API Key**: Unlike commercial geocoding services (Google Maps, Mapbox), Nominatim is free but has strict usage policies. The current implementation doesn't include any contact information in the user-agent, which violates their terms of service.

3. **Rate Limiting**: Without proper identification, requests are likely being throttled or rejected, especially if multiple searches are performed in quick succession.

### **Secondary Issues Identified:**

- **No retry logic**: The code has a 10-second timeout but no retry mechanism for transient failures
- **Generic error handling**: The frontend shows "Failed to find location" without exposing the actual error details from the backend
- **No fallback service**: If Nominatim is down or blocking requests, there's no alternative geocoding provider

### **Recommended Fixes:**

1. **Update user-agent** to include contact information:
   ```python
   geolocator = Nominatim(user_agent="astrophotography-target-finder/2.0 (your-email@example.com)")
   ```

2. **Consider alternative services** like Mapbox, Google Geocoding API, or Here Maps (all require API keys but have more generous rate limits)

3. **Add retry logic** with exponential backoff for transient failures

4. **Improve error messaging** to surface actual error details to help diagnose issues

The location search is failing because Nominatim is rejecting requests due to the non-compliant user-agent string. This is a common issue when using free geocoding services without proper identification.

I've identified the root cause of the "calculation error telling me to input equipment details when everything is filled in" issue.

### The Problem

There's a **critical mismatch between frontend validation and backend requirements** for equipment data:

**Frontend Validation Issue** ([`index.astro:169-171`](astrophotography-engine/frontend/src/pages/index.astro:169-171)):
```typescript
if (!equipment.aperture_mm || !equipment.focal_length_mm) {
    throw new Error('Please enter your equipment details');
}
```

**Frontend Data Storage** ([`EquipmentForm.astro:322-336`](astrophotography-engine/frontend/src/components/EquipmentForm.astro:322-336)):
- Stores **EITHER** `aperture_mm` **OR** `f_number` (never both)
- When user toggles to f-number mode or selects a lens preset, only `f_number` is stored
- The `aperture_mm` field is omitted from sessionStorage

**Backend Accepts Both** ([`request.py:12-29`](astrophotography-engine/backend/app/models/request.py:12-29)):
- Backend's `EquipmentModel` accepts either `aperture_mm` OR `f_number`
- Has a `get_aperture_mm()` method to calculate one from the other

### Why It Fails

1. User selects a camera lens preset (e.g., "135mm f/2") or toggles to f-number mode
2. Form stores `f_number` but NOT `aperture_mm` in sessionStorage
3. Frontend validation checks for `aperture_mm` presence
4. Validation fails even though all fields are filled
5. User sees error: "Please enter your equipment details"

### The Fix Required

Update the validation in [`index.astro:169-171`](astrophotography-engine/frontend/src/pages/index.astro:169-171) to accept either field:

```typescript
// Current (WRONG):
if (!equipment.aperture_mm || !equipment.focal_length_mm) {
    throw new Error('Please enter your equipment details');
}

// Should be:
if ((!equipment.aperture_mm && !equipment.f_number) || 
    !equipment.focal_length_mm || 
    !equipment.sensor_width_mm || 
    !equipment.sensor_height_mm) {
    throw new Error('Please enter your equipment details');
}
```

This validation will:
- Accept either `aperture_mm` OR `f_number` (matching backend logic)
- Also validate sensor dimensions (currently missing from validation)
- Allow both telescope and lens configurations to work properly
